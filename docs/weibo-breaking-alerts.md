# 微博突发爆点提醒运维说明

## 作用与接收者

服务每 30 分钟抓取一次完整微博热搜榜，比较相邻的完整快照并识别可能的突发爆点。进程启动后，第一轮只写入基线快照和事件状态，**不会发送提醒**；从第二轮开始才会比较变化。

提醒只通过 qq-bot 的 `QQBotService.Notify` 发送：

```proto
rpc Notify(NotifyReq) returns (Resp) {}

message NotifyReq {
  string content = 1;
}
```

调用不使用 `SendMsg`，不携带群号、QQ 号或收件人列表。实际接收者完全由 qq-bot 当前已有的“微博热搜订阅”决定；qq-bot 对这些订阅者扇出。单次 `Notify` 即使投递给多个订阅者，也只算一个事件提醒。

## 判定规则

所有网页解析得到的 `tags` 都按原始顺序保存和透传；不会将 `爆`、`荐`、`新`、`沸` 等标签丢弃或改写。

一个条目须先满足至少一个强信号，且总分达到 5 分，才会被作为爆点通知：

| 规则 | 条件/分值 |
| --- | --- |
| 新上榜强信号 | 新出现且进入 Top 10；计 2 分 |
| 排名跃升强信号 | 排名提升至少 15 位且进入 Top 20；提升 15–29 位计 2 分、至少 30 位计 3 分 |
| 热度上涨强信号 | 热度至少翻倍且进入 Top 20；增长 100%–199% 计 2 分、至少 200% 计 3 分 |
| 爆点标签强信号 | 位于 Top 20 且含 `爆`、`沸` 或 `当前爆词`；计 3 分 |
| 排名加分 | Top 3 / Top 10 / Top 20 分别计 3 / 2 / 1 分 |
| 其他标签加分 | 含 `新` 或 `荐` 计 1 分（两者同时出现仍只计一次） |

标签只影响评分，不能绕过上述 Top 20 / Top 10 的强信号边界。标题会做全半角和空白归一化，作为第一版事件键；不同标题不会被主动合并为同一新闻。

## 去重、完成与额度

- 同一事件首次成功交给 qq-bot 后不再因排名、热度或标签变化重复推送。
- 一个事件连续两次不在榜，或连续两次排名下降后完成；完成后不再推送。
- 完成事件必须已沉寂至少 12 小时，并且在相邻完整快照中真正重新出现且进入 Top 10，才开启新的事件轮次。一直留在榜上的完成事件不会重开。
- 按上海自然日全局最多发送 5 个事件；额度按事件而非订阅者人数计算。超过上限的事件会被记录为已抑制，次日也不会补发。
- qq-bot 成功返回 `没有可推送的订阅者` 时，事件终止且不占用额度；RPC 明确报错时，只在下一次采样重试一次，第二次失败后终止。

通知正文是纯文本，例如：

```text
💥💥💥 微博突发爆点
【孙宇晨说长文写了十几个小时】
排名：新上榜 → 第1
标签：当前爆词
触发：新上榜 + Top 10 + 爆点标签
链接：https://weibo.com/xxxx
```

没有标签时会省略“标签”行。

## 配置与持久化

启用监控需要以下环境变量：

| 变量 | 用途 | 要求 |
| --- | --- | --- |
| `WEIBO_COOKIE` | 现有微博网页抓取器的 Cookie 值 | 使用有效值；仅在部署平台的 Secret/密钥管理中配置，绝不提交到仓库或日志 |
| `QQ_BOT_GRPC_ADDR` | qq-bot 的 gRPC 地址 | 必填，例如部署网络内可解析的地址；不要写入接收者信息 |
| `WEIBO_ALERT_STATE_PATH` | SQLite 事件、快照和每日额度状态文件 | 必填，且必须落在已挂载的持久卷内 |

容器的临时文件系统不能作为 `WEIBO_ALERT_STATE_PATH`。部署时应将持久卷挂载到一个目录，再把变量指向该目录中的具体文件，例如“已挂载目录下的 `weibo-alerts.sqlite3`”。若现有部署使用 Kubernetes，应以 Secret 引用注入 `WEIBO_COOKIE`，并让 `volumeMount` 覆盖该状态文件所在目录；本仓库目前没有 Kubernetes 或 Compose 部署清单，因此没有提供或假定集群、命名空间或 Secret 名称。

若 `QQ_BOT_GRPC_ADDR` 或 `WEIBO_ALERT_STATE_PATH` 缺失，或监控初始化失败，服务会记录“monitor disabled”日志并仅禁用这项告警；既有 Bing 壁纸定时任务继续运行。Cookie 无效等抓取失败会被本轮调度边界记录，下一轮仍会继续尝试。

## 崩溃边界与投递语义

`Notify` 只有 `content` 字段，没有调用方可用的幂等键，也无法得到 QQ 对端的送达回执。服务在发起 RPC 前会把事件持久化为 `DISPATCHING`：

- 如果 RPC 明确返回错误，服务知道本次没有完成，可在下一轮最多重试一次。
- 如果进程在 qq-bot 已接受消息之后、但在本地完成状态结算之前崩溃，重启后会保留 `DISPATCHING` 并**不重发**。这优先避免用户看到重复消息，但意味着该次远端结果是未知的。
- 已知成功会结算当天额度并进入已通知状态；无订阅者或最终失败会释放预留额度。

日志只包含事件键、评分、状态转换和结果，不包含 Cookie、订阅者、群号或 QQ 号。

## 上线核验清单

1. 在部署平台确认 Cookie 由 Secret/密钥管理注入，确认 qq-bot 地址可达，并确认状态文件目录是持久卷且进程可写。
2. 重启服务后观察首轮日志：应建立基线，且不应出现 `Notify dispatch started` 或 QQ 消息。
3. 等待下一次 30 分钟采样，确认日志只在满足评分与强信号条件时记录 eligible/dispatch；常规榜单变化不应推送。
4. 使用已开启微博热搜订阅的测试群或私聊验证纯文本格式；临时没有订阅者时，确认 qq-bot 返回“没有可推送的订阅者”，服务不报为投递成功且不消耗五条额度。
5. 连续触发六个合格事件，确认同一上海自然日仅前五个调用 `Notify`；检查相同事件后续快照不会再次发送。
6. 在可控环境模拟一次明确 RPC 失败，确认仅在下一采样周期重试一次；不要为了验证而人为制造 `DISPATCHING` 崩溃场景于生产环境。
